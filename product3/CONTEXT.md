## 0. 为什么做产品③（作品集视角）

已交付两产品覆盖的能力：

| 能力 | 产品① meeting-digest | 产品② content-studio |
|---|---|---|
| LLM 同步生成 + 结构校验 | ✅ 6 板块强校验 | ✅ 笔记 JSON 结构 |
| 流式输出（SSE） | — | ✅ step/token/done 协议 |
| 抓取 / 解析 | — | ✅ fetch + linkedom 启发式 |
| 持久化 | ❌ 无状态（隐私最小化） | ✅ D1 + 历史/删除/重生成 |
| 鉴权 | 可选令牌 | ✅ 令牌 + 401 契约 |
| 异步长任务 / 定时 | — | — |
| 真实浏览器能力 | ❌（沙箱限制，靠外部 ego-browser） | — |
| 检索（向量/RAG） | — | — |
| 多轮状态（会话） | — | — |
| 人机协同（审批节点） | — | — |

**缺口 = 产品③ 的选题空间**：异步/定时、真实浏览器、检索、多轮状态、人机协同、评测。

**红线（反同质化）**：不再做第三个「贴文本 → 生成文本」的工作台。产品③ 必须引入**新的平台能力**或**新的交互范式**（长任务 / 浏览器 / 检索 / 多轮 / 审批）。

## 1. 平台可行性（已核实，2026-10）

| 能力 | 现状 | 对产品③ 的含义 |
|---|---|---|
| `Void 1.2.1` `cloudflare` 配置支持的绑定 | `d1_databases` / `kv_namespaces` / `r2_buckets` / `hyperdrive` / **`queues`（producers+consumers）** / **`triggers.crons`** / `assets` / `send_email` | 异步任务（Queues）与定时（Cron）**是一等公民**，无需绕开配置权威源 |
| Durable Objects | ❌ `CloudflareConfig` 无该字段 | 会话/状态机用 D1 + Queues 实现，不引入 DO |
| Cloudflare Workflows | ❌ 同上（且需原生 wrangler 直连，破坏「void.config.ts 是唯一权威源」） | **不选依赖 Workflows 的方案** |
| Browser Run（Browser Rendering） | Free：**10 分钟/天**；Paid：10 小时/月（$0.09/浏览器小时） | 真实浏览器可行，但必须按「手动触发 + 单次 1–2 分钟」设计 |
| Vectorize | Free：5M 存储维度、30M 查询维度/月、100 索引 | 轻量 RAG 可行 |
| `send_email` 绑定 | ✅ 配置层支持 | 可做「邮件交付」形态（无需自建 SMTP） |

沙箱已知约束（沿用产品①②）：`vite dev` / workerd 不可 spawn（本地用 Node shim 验证，真启动验证放 CI）；`npm install --ignore-scripts`；部署走 `npm run deploy`。

## 2. 候选清单

评分维度：**FDE 叙事强度**（能否讲清"我在交付而不是在玩 demo"）、**新技术含量**、**复用度**、**演示直观度**、**工作量**、**风险**。

### A. 交付验收机器人（acceptance-bot）★ 推荐

输入一条线上 URL + 一份验收清单（YAML/Markdown 勾选项）→ 用 **Browser Run 真浏览器**执行步骤（打开、点击、填表、断言文案）→ 产出**证据包**（每步截图 + 断言结果 + 耗时 + 失败定位 + Markdown 报告）。

- **FDE 叙事**：★★★★★ 这就是 FDE 每天在做的事——"交付不是我说好了，而是有证据"。与两产品的 E2E 实践、`product1/docs/e2e-evidence/` 方法论完全同源。
- **新技术**：Browser Run（真实浏览器）+ 异步任务（Queues）+ 报告产物（R2/静态）
- **复用**：Void 结构、令牌保护、错误收敛、部署脚本、CI、Node shim 模式
- **演示**：输入 URL+清单 → 90 秒后出报告（截图墙 + 红绿断言），面试官可当场给个自己的站点测
- **工作量**：中（4–6 天量级）
- **风险**：① 免费配额 10 分钟/天 → 缓解：手动触发 + 单次上限 + 步骤数上限；② 步骤 DSL 越做越大 → 缓解：MVP 只支持 5 个动作（goto/click/fill/expectText/expectVisible）+ 截图；③ 只能在 Worker 内跑 Browser Run（不能本地跑）→ 缓解：结果全落库，本地只测纯函数（DSL 解析/断言求值/报告渲染）

### B. 交付规格生成器（spec-forge）

粘贴客户访谈记录 / 需求文档 → **多轮追问**（缺什么问什么）→ 输出验收标准 + 边界 + 风险 + 工作量拆解 + 可直接交接的 Markdown 包。

- **FDE 叙事**：★★★★★（面试官就是客户："你给我做个需求澄清"）
- **新技术**：多轮会话状态（D1）+ 缺口检测 + 结构化输出校验（可加"覆盖率评分"）
- **复用**：产品① prompt/校验/注入防护、产品② D1 与会话
- **演示**：强（对话式，现场问答）
- **工作量**：小–中（2–3 天）
- **风险**：技术含量最低（本质 Prompt 工程 + 状态），容易被看成"又一个聊天框"；若无评分/覆盖率/缺口检测等硬机制，简历信号弱

### C. 企业知识库问答（kb-qa，RAG）

多源（URL / Markdown / 纯文本）→ 切分 + 嵌入 Vectorize → 检索 + **引用溯源** + 无答案拒答 + 检索评测集（Recall@k / 拒答率）。

- **FDE 叙事**：★★★★（企业落地最常见场景）
- **新技术**：RAG 全链路 + 向量检索 + 评测集（这是作品集里最能证明"我懂质量"的部分）
- **复用**：产品② 抓取与文本处理
- **演示**：中（问答本身直观，但"引用对不对"要内行才看得出价值）
- **工作量**：大（6–10 天：PDF/中文切分、嵌入配额、评测集构造）
- **风险**：① PDF 解析在 Worker 内存/CPU 限制下麻烦；② 中文切分质量决定一切；③ 检索效果不达标会变成"看起来很唬人但不好用"

### D. 多 Agent 交付流水线（agent-runtime）

把「需求 → 方案 → 实现清单 → 验收」做成可恢复长任务：Queues 拆步 + D1 状态机 + **人工审批节点** + 全链路审计日志。

- **FDE 叙事**：★★★（基础设施视角，业务方难共鸣）
- **新技术**：★★★★★（编排、状态机、重试、审批、审计——但**不能用 Workflows/DO**，需自建，复杂度陡增）
- **工作量**：大（8–12 天）
- **风险**：高。Queues consumer 的 CPU/时长边界 + 自建状态机的幂等性，容易做成"能跑但脆"的系统；演示弱

### E. 定时情报雷达（cron-radar）

每天 Cron 抓 N 个源（RSS/网页）→ 变更检测 + 摘要 → 生成日报页 + 邮件推送（`send_email` 绑定）。

- **FDE 叙事**：★★★☆
- **新技术**：Cron + 增量状态（去重/变更检测）+ 邮件交付 + 成本控制
- **风险**：与产品①「日报」概念重叠，容易被读成"产品① 加个定时器"；演示需要等一天

## 3. 推荐：A（交付验收机器人），并把 B 的「验收清单生成」作为可选二期

| 标准 | A | B | C | D | E |
|---|---|---|---|---|---|
| FDE 叙事 | ★★★★★ | ★★★★★ | ★★★★ | ★★★ | ★★★☆ |
| 新技术含量 | ★★★★（Browser Run+Queues） | ★★ | ★★★★★ | ★★★★★ | ★★★ |
| 复用度 | ★★★★ | ★★★★★ | ★★★☆ | ★★★ | ★★★★ |
| 演示直观 | ★★★★★ | ★★★★ | ★★★ | ★★ | ★★ |
| 风险可控 | ★★★★ | ★★★★★ | ★★★ | ★★ | ★★★★ |
| 工作量 | 中 | 小 | 大 | 大 | 中 |

**选 A 的四条理由**：
1. **叙事不可替代**：作品集里已有"能生成"，缺的是"能证明生成的东西真的能用"——验收证据是 FDE 交付的最终货币。
2. **补齐最尖锐的能力缺口**：真实浏览器 + 异步任务，两者都是企业 AI 落地的高频刚需，且都是现有两产品完全空白。
3. **方法学一致**：产品①② 的 E2E 证据、1101 探针、`perf-hang-triage` 经验可直接内化为产品能力（不是新开一条技术线，而是把已有实践产品化）。
4. **风险有明确边界**：配额（10 分钟/天）用"手动触发 + 上限"就能兜住；最坏情况退化成"单页截图 + 断言"，仍然可用。

**明确不选 D 的理由**：Void 配置层不支持 Workflows/DO，自建状态机是"为了炫技而承担不可控复杂度"，与奥卡姆剃刀冲突。

## 5. 验收标准草案（若选 A；待第 2 步收敛后写死）

1. 输入「URL + 验收清单（YAML）」→ 创建一次验收任务并返回任务 ID
2. 任务在 Browser Run 中执行 5 类动作：`goto` / `click` / `fill` / `expectText` / `expectVisible`
3. 每步产出：结果（pass/fail）、耗时、失败原因（选择器未命中 / 文案不符 / 超时）、截图
4. 全部步骤完成后生成 Markdown 报告：通过率、逐步明细、失败截图内嵌、总耗时
5. 报告与截图持久化（D1 存任务与步骤结果，截图存 R2），刷新后可回看历史任务
6. 配额守卫：单任务步骤数上限、单任务总时长上限、超限明确报错且不产生半成品报告
7. 失败可诊断：任务失败时报告明确给出「第几步 / 期望 vs 实际 / 建议排查方向」
8. 令牌保护：无令牌不可创建/读取任务；401/403 契约与产品② 一致
9. 零密钥前端：Browser Run 与 LLM 凭据仅存 Worker env
10. 自证闭环：用产品③ 对产品①/② 的线上地址跑一份验收清单，产出可归档的证据包
