## 4. 决策记录（对齐轮次结论，只增不改）

  ② 扫描件/照片 OCR（复用③ 链路模式，兑底）③ 手工录入（补漏/快速记复查）。
- **D3 指标范围**：**不设白名单** —— 报告里有什么指标就抽什么入库；另设「趋势图推荐清单」

  不限制入库范围。
- **D4 参考范围口径**：以**报告原文为准** —— 每次检测的参考范围随指标行入库
  （`ref_low`/`ref_high`/`ref_text`），异常判定用**当次报告自己的范围**；
  跨次对比时若范围变化须可见（标注「参考范围已变」）。不内置「标准范围」
  （不同医院/方法学范围不同，内置反而是错的）。
- **D5 AI 解读边界（红线）**：只做三件事 —— 指标含义解释 / 趋势变化描述（结合本人历史）/
  复查建议方向（挂什么科、复查什么项目）。**不做**：诊断、用药建议、危急值报警；
  依据不足明确拒答（与③ 纪律一致）；解读页固定免责声明；红线用例进评测集。
- **D6 验收口径**：按 §5 A1–A8 执行（含抽取准确率评测集标定、令牌保护、隐私声明）。

## 已确认方案（第 3 步 design-plan 产出，2026-10-29，待 3.5 复核授权）

### 问题本质（一句话）

把「躺在抽屉里的体检报告」变成**可信的健康时间序列**，并在其上做**有纪律的 AI 解读**。
两个真难点：① 非结构化报告 → 可信结构化指标（数值错一位就是医疗数据事故，趋势与异常
判定全建立在数值上）；② 解读红线（不装医生）。

### 方案对比（实现路径）

| | 方案 A：文本先行 + LLM 抽取 + 人工确认闸（**推荐**） | 方案 B：规则引擎抽取 | 方案 C：视觉模型一步出 JSON |
|---|---|---|---|
| 做法 | PDF 文字层 / OCR 文本 / 手工录入 **三条输入汇合到同一个「文本 → LLM 结构化」环节**；指标 JSON 带 `source_quote`（原文片段）；校验失败重试（同①）；**人确认页展示抽取结果+原文对照，勾选后才入库** | 按医院模板写正则/规则库 | 扫描页图直接丢给视觉模型出 JSON，省掉文本环节 |
| 收益 | 抽取逻辑只有一份，评测只标定一个环节；人工确认闸兑底抽取错误；`source_quote` 让每条数值可对照原文（引用可核验思想迁移到抽取） | 确定性强、无模型成本 | 链路最短 |
| 代价 | 多一步人工确认（每份报告 ~10 秒） | 体检报告格式千差万别，规则库维护无底洞 | 视觉模型**数值抽取**精度未验证（③ 只验证了文本识别质量）；错一个数量级直接进库 |
| 风险 | LLM 幻觉数值 → 由确认闸+评测集控制 | 长尾格式永远修不完 | 数值错误不可控 |
| 结论 | ✅ 采纳 | ❌ 落选 | ❌ 落选（OCR 降级为文本获取的兑底路径，不直接出结构化数据） |

### 落选候选清单（库/依赖级）

| 候选 | 筛掉原因 | 复活条件 |
|---|---|---|
| recharts / echarts | 体积大、SSR 兼容要配置；需求只是折线+范围带 | 趋势图需求超出折线+范围带（多指标叠加/缩放/导出） |
| Zod | 手写校验模式①已验证，少一个依赖 | 校验规则复杂到手写难维护 |
| Vectorize / 知识库 | 解读的数据全在 D1 行里（本人历史），不需要语义检索；指标解释靠模型知识+拒答纪律，建知识库范围爆炸 | 模型对指标含义解释质量实测差 → 二期考虑小型指标知识库 |
| Durable Objects / Cron / Queues | 首发手动触发，无异步编排需求 | 接定时巡检/自动周报（产品④二期） |
| Workers AI 直接抽取 | 网关模型结构化输出①已验证更稳 | 网关配额/可用性问题 |

### 推荐方案（架构与模块）

**数据流**：`PDF(文字层)/扫描件(OCR)/手工录入 → 报告文本 → LLM 结构化抽取（带 source_quote）
→ 校验+重试 → 人工确认页（对照原文勾选）→ 入库 → 趋势/异常/解读`。

- **D1 建模**（migration `0001_reports_metrics.sql`）：
  `reports`(id, profile_id DEFAULT 'default', source_type pdf/ocr/manual, file_name,
  check_date, hospital, raw_text, created_at) +
  `metrics`(id, report_id, profile_id, standard_name, raw_name, value, unit,
  ref_low, ref_high, ref_text, status normal/high/low/unknown, source_quote, created_at)。
  趋势按 `standard_name + profile_id` 聚合。
- **指标名归一**（真设计点）：不同医院叫法不同（「甘油三酯/TG/Triglyceride」）→ 抽取
  prompt 内置标准指标字典（~20 高频指标，实现阶段随评测语料定死清单），输出
  `{standard_name, raw_name}` 双写；没匹配上的开放指标用 raw_name 聚合。防趋势断裂。
- **异常判定宁缺毋滥**：参考范围格式千奇百怪（`60-100` / `≤100` / 文字描述）→
  `ref_text` 原文必存；结构化 `ref_low/high` 解析得出才判 status，**解析不出只存原文、
  status=unknown，不标异常**（宁可不标，不可错标）。
- **模块**：`lib/extract.ts`（文本→指标 JSON+校验+重试）、`lib/trend.ts`（趋势聚合/异常判定
  纯函数）、`routes/api/reports.ts`（上传/列表/详情/删除）、`routes/api/metrics.ts`
  （手工录入）、`routes/api/interpret.ts`（解读）、`pages/index.tsx`（导入/时间线/解读）+ SVG 图表组件。
- **AI 解读**（`interpret.ts`）：拉该指标全历史 + 当次详情进 prompt（引用=数据行，可核验）；
  system prompt 写死红线（不做诊断/用药/危急值）；仅 1 次数据只解释含义不做趋势判断；
  无该指标知识/数据不足 → 明确拒答；页尾固定免责声明。
- **鉴权/隐私**：`ACCESS_TOKEN` 令牌（`lib/http.ts` authorize 模式，②③同源）；无第三方
  上报、无分析脚本；raw_text 全文入库（单用户自托管，复核需要）。
- **评测**：`eval/cases/` 抽取用例 ~30 例（人工标注 JSON）；准确率口径：**行级为主**
  （整条指标四元组 名称/数值/单位/范围 全对才算对）+ 字段级为辅（定位弱点）；
  另含红线用例（解读请求要诊断/用药 → 必须拒答）。
- **M0 前置验证**：新 Worker 骨架（void.config.ts 只带 D1+AI，无 Vectorize）+
  migration 0001 + 一条「文本→抽取→入库→查询」最小链；风险已在③验证过，M0 预计顺利。

复核无问题的方向（明确记录，避免以后重复审查）：
- **确认闸不可绕过**：入库路由对每一行重新计算，客户端伪造 `status`/`valueNum`/`refHigh` 全部被覆盖（有单测）。

- **XSS**：`rawText` 与模型文本一律经 React 转义渲染（`<pre>{...}</pre>`、表格单元格），无 `innerHTML`。
- **401 契约**：所有 `/api/*`（除 `/api/health`）统一 `authorize()`，有覆盖测试。

### 7.2 Requirement Clarification Summary（`clarify-requirements` 模板，补做）

**Feature:** health-track（体检指标追踪）

#### 1. Business Goal
- **Core problem**：体检报告躺在抽屉里 —— 单次数值看不出跨年趋势，异常项看不懂含义，年年重复检查却没人回答「这条线在变好还是变坏」。
- **Target users**：本人（单人自用，D1）；不做多人协作/家庭多成员（表已预留 `profile_id`）。
- **Main scenario**：导入一份新报告 → 核对抽取结果 → 入库 → 与历史对比看趋势 → 对异常指标要一个「不越界」的解释。

#### 2. Data Spec
- **Inputs**：电子版 PDF（有文字层）/ 扫描件或图片型 PDF（≤5 页，走 OCR）/ 手工录入 / 粘贴文本。
- **Outputs**：结构化指标行（名称、归一标准名、数值、原文值、单位、参考范围原文与解析出的上下限、状态、原文片段）；趋势序列；解读文本 + 引用数据行 + 免责声明。落库为 D1 `reports` + `metrics`。

#### 3. Edge & Exception Handling

| Scenario | Behavior |
|---|---|
| 空文本 / 只有空白 | 400，不调模型 |
| 文本超长 | 400（抽取上限 60000 字符）/**413**（入库上限 200000）—— **不静默截断**（截断会漏指标） |
| PDF 无文字层 | 明确提示走 OCR，不假装成功 |
| OCR 单页失败 | 只跳过该页并在文本里留可见标记，不整批失败 |
| 模型输出非 JSON / 缺检测日期 / 指标全丢 | 重试 1 次；仍失败 → 502 且文案可读 |
| 上游 401/429/5xx | **不重试**（避免放大限流），映射为友好文案 |
| 参考范围解析不出（`阴性`/文字描述/罕见写法） | `status=unknown`，**不判异常** |
| 定性值（阴性）/`<0.01` | `value_num=null`，不成趋势点，不插值 |
| 跨次单位变化（mmol/L ↔ mg/dL） | `unitChanged=true` + 前端红色告警（折线不可直接比较） |
| 同指标跨次参考范围变化 | `refChanged=true` + 前端标黄 |
| 解读时无该指标数据 | 200 + `refused/no_data`（**不是错误码**），不调模型 |
| 解读提问命中诊断/用药/危急 | 200 + `refused/question_guard`，不调模型 |
| 并发冲突（同日两次手工补录） | 单用户低概率：可能产生两份手工报告（见 §8 已知限制） |
| 未带令牌 | 401（所有 `/api/*` 除 `/api/health`） |

#### 4. Constraints
- **Tech stack**：Void（Vite 8 / Rolldown）+ React 19 SSR + Hono + Cloudflare Workers + D1 + Workers AI + magpie 网关。
- **Performance**：首页 SSR < 1s（实测资产 4969 字符 HTML）；抽取单次 5–40s（上游模型决定）；趋势聚合纯内存（上限 20000 行）。
- **Security**：`ACCESS_TOKEN` 承载访问控制；无第三方上报；OCR 只收 data URL（不 fetch 任意 URL，避免新增 SSRF 面）；密钥只在 Worker env。
- **Browser/Platform**：现代浏览器（PDF 抽取依赖 pdf.js + canvas，仅浏览器端）。

#### 5. Acceptance Criteria
见 §5 的 A1–A8（已写死），本节不重复。

#### 6. Terminology Dictionary

| Business Term | Code Naming | Description |
|---|---|---|
| 报告 | `Report` / `reports` | 一次检测的快照（含原文全文） |
| 指标 | `Metric` / `metrics` | 报告中的一行（一个检测项） |
| 标准指标名 | `standardName` | 归一后用于趋势聚合的名字 |

| 参考范围 | `refText` / `refLow` / `refHigh` | 原文永远保留；上下限仅在可解析时才存在 |
| 状态 | `status` | `normal`/`high`/`low`/`unknown`（服务端确定性计算） |
| 原文片段 | `sourceQuote` | 报告原文中该指标所在片段（人工复核锚点） |
