## 1. 一句话与整体架构

**一句话**：把「URL 抓取或粘贴文本」经三步流水线（抓取 → 素材准备 → 生成）转成小红书图文笔记，全程 SSE 流式反馈，结果落 D1 作历史。

```
浏览器（React SSR + connectEventStream）
   │  POST /api/generate { sourceType, url?/text?, variation? }
   │  Authorization: Bearer <ACCESS_TOKEN>
   ▼
Cloudflare Worker（content-studio，同源 /api/* 文件即路由）
   │
   ├─ routes/api/generate.ts   SSE 入口：令牌 → 请求体校验 → 流水线 → 落库
   ├─ routes/api/jobs.ts       历史：GET 列表 / GET 单条 / DELETE
   ├─ routes/api/health.ts     健康检查
   │
   ├─ lib/pipeline.ts          三步编排（依赖注入，不落库）
   │    ├─ lib/fetch-article.ts   URL→正文（linkedom + SSRF 三道闸）
   │    ├─ lib/llm.ts             callLLM（压缩）/ streamLLM（生成，流式）
   │    ├─ lib/prompt.ts          压缩 prompt + 笔记 prompt（行级标记格式）
   │    └─ lib/note.ts            解析 / 校验 / 流式预览 / 兜底
   ├─ lib/store.ts             JobStore 接口 + D1 实现 + 内存实现
   └─ lib/auth.ts / lib/http.ts  令牌校验 / env 解析 / 错误 JSON 契约
   │
   ▼
外部：magpie 网关（OpenAI 兼容 /chat/completions，stream:true）
存储：Cloudflare D1（content-studio-db，单表 jobs）
```

技术栈：Void 1.2.1（Vite + Rolldown + React SSR）+ Cloudflare Workers + D1。与产品①同栈，平台层全部复用产品①已验证资产（令牌保护、magpie 接入模式、部署管线、skill 沉淀）。

## 2. 一次生成的完整生命周期

以「贴 URL，素材 8000 字」为例（线上实测时间线）：

```
t=0      浏览器 POST /api/generate（带 Bearer token）
t≈0ms    Worker：令牌校验 → 请求体校验（sourceType/长度前置闸）→ magpie 配置检查
         开 SSE 流（200 text/event-stream）
t≈8.9s   step:fetch started → done   「已抓取 N 字 · <标题>」
         （Workers fetch + linkedom 抽正文，10s 超时，2MB 上限）
t≈9s     step:prepare started        「素材 8,000 字，正在压缩要点…」
         callLLM 非流式：长文 → ≤800 字要点（保留事实/数据/金句）
         压缩后重校硬上限 30,000（防模型返回超长「要点」）
t≈17.3s  step:generate started       streamLLM 流式（temperature 0.7）
         每个 delta → 一个 token 事件 → 浏览器逐字渲染
         （首个 token 前的等待期由步骤进度覆盖，实测可达 8–23s）
t≈17.5s  流结束 → parseNote 解析 → isUsableNote 校验
         → 越界项（长度/标签数/emoji）产出非致命 warnings
         → store.insert(job) 落 D1（成功后才落库，失败/中断不留半截记录）
         → done 事件 { job, persisted, warnings }
         → finally stream.close()（清理 keepAlive interval）
```

**文本输入路径**：步骤 1 直接 emit `skipped`（「使用粘贴文本」），其余相同；素材 ≤6000 字时步骤 2 同样 `skipped` 直通。

## 3. SSE 事件协议

`POST /api/generate` 返回 `text/event-stream`，四种事件（`lib/types.ts` 的 `PipelineEvent` 为源）：

| 事件 | data 结构 | 时机 |
|---|---|---|
| `step` | `{ type:"step", step:"fetch"\|"prepare"\|"generate", status:"started"\|"done"\|"failed"\|"skipped", detail? }` | 每个流水线阶段边界 |
| `token` | `{ type:"token", text }` | 生成阶段每个上游 delta |
| `done` | `{ job, persisted, warnings? }` | 流水线成功 + 落库后 |
| `error` | `{ phase, message, hint? }` | 任一阶段失败（fetch 失败附「改用粘贴文本」引导） |

**状态码与流的分工**：流未开始时用 HTTP 状态码（401 令牌 / 400 请求体 / 503 未配置上游）；开流后 HTTP 已是 200，一切失败只能走 `error` 事件。`message` 一律是用户可读文案，不含堆栈。

**客户端消费**（`lib/client-stream.ts` + `pages/index.tsx`）：
- `AbortSignal` + 90s 空闲超时；`try/finally` 统一 `setRunning(false)`，保证任何异常路径按钮都能恢复。
- 「未见 done 即流结束」视为异常结束，不留悬挂的「生成中」状态。
- 并发闸：`abortRef` 防两条流 token 交错（重新生成期间再点生成会被拒）。

**服务端防御**：handler 末尾 `finally { stream.close() }` —— `void/sse` 的 keepAlive 是 `setInterval`，部分收尾路径不会自动清理，不关会在 isolate 里留下永久 interval（实测会让 Node shim 进程挂住不退出）。

## 4. 模块职责与分层原则

分层原则（design-plan 定稿）：**流水线各阶段互不依赖，靠数据结构衔接；LLM/抓取/存储全部接口化可注入**。

| 模块 | 职责 | 关键点 |
|---|---|---|
| `lib/pipeline.ts` | 三步编排，产出 `GenerationJob` + 非致命 `warnings` | 依赖注入（`PipelineDeps`）；**不落库**（落库在路由层，流失败不留半截记录）；常量 `COMPRESS_THRESHOLD=6000` / `HARD_CAP=30_000` |
| `lib/fetch-article.ts` | URL → 正文 | linkedom 静态解析 + 正文启发式；SSRF 三道闸；10s 超时、2MB 上限、**不做重试**（奥卡姆：重试解决不了动态渲染/登录墙，只拖长等待） |
| `lib/llm.ts` | magpie 接入 | `callLLM`（非流式，压缩，85s 超时）/ `streamLLM`（流式 async generator，120s 超时）；错误收敛为 `MissingConfigError` / `LLMError`，文案面向用户 |
| `lib/prompt.ts` | 两个 system prompt | 压缩（条目式 ≤800 字，保事实/数据/金句）；笔记（行级标记格式 + 口语化 + 忠于素材 + 防臆造）；`variation` 扰动提示防重复输出 |
| `lib/note.ts` | 解析/校验/兜底 | 行级标记正则**全站唯一**（`parseNote` 与 `previewBody` 共用）；宽容解析（全角括号/Markdown 标题/缺段）；无标题时从正文首句截取兜底 |
| `lib/store.ts` | 历史 CRUD | `JobStore` 接口；D1 实现（最小 API 子集，不引 ORM）+ 内存实现（测试/shim）；列表只取显式列（不搬运 50×3 万字原文）；删除用 `DELETE ... RETURNING` 单次判定 |
| `lib/auth.ts` / `http.ts` | 令牌 / env / JSON 契约 | 令牌校验只有一处实现；`_fetchImpl` / `_store` 测试注入口 |
| `routes/api/generate.ts` | SSE 入口 | 校验（令牌→请求体→配置）→ 开流 → 编排 → 落库 → 关流 |
| `routes/api/jobs.ts` | 历史路由 | GET 列表（最多 50，不含全文）/ GET?id 单条（含 sourceText 供重新生成）/ DELETE?id |

## 5. 关键设计决策与原理

### 5.1 为什么输出用「行级标记」而不是 JSON
正文需要 **token 级流式展示**。JSON 在流中途不可读，用户会看到 `{"body":"...` 的噪音。
改为行级标记（`[标题]` / `[备选标题]` / `[正文]` / `[标签]`），前端流式中用 `/^\[.+\]$/` 隐藏标记行，正文照常逐字出现。生成完成后 `parseNote` 一次性解析为 `XhsNote { titles[], body, tags[] }`。

### 5.2 落库时机 = 流水线成功之后
对抗性审查的反例「流式响应中途失败，历史里残留半截记录」成立 → **流中不写库**；完成时（含 succeeded）才 `insert`。副作用：中断 = 无记录，前端对已渲染的 token 提示重试。
存储失败的兜底：笔记照常经 `done` 返回（`persisted:false` + warning「请自行复制留存」），不让存储故障吞掉用户已看到的结果。

### 5.3 超长素材自动压缩（相对产品①的升级）
产品①对超长输入仅报错；本产品 URL 场景下网页正文常超 6000 字，自动压缩是体验必需：
- `>6000` 字 → `callLLM` 压缩为要点（保留核心观点/事实/数据/金句/结论）；
- 压缩后**再校硬上限 30,000** —— 模型可能返回超长「要点」，不拦会把超长 prompt 送进生成，上游 400/413 会被误归成「AI 服务暂不可用」；
- 压缩是**有损风险**接受项：prompt 要求保真，质量靠 E2E 检验，不达标调 prompt。

### 5.4 错误分类与文案透传
```
MissingConfigError → 503（未配置上游凭据）
LLMError           → 5xx 语义（凭据无效 / 429 限流 / 上游 5xx / 空结果 / 超时 / 上游中断）
PipelineError      → 带 phase 的用户可见错误（fetch/prepare/generate）
FetchArticleError  → 带 code（invalid_url / blocked_host / network / http_status / empty）
```
关键原则：**自定义错误的 message 直接上屏，未知异常统一兜底「生成失败，请稍后重试」并打服务端日志**。早期版本在这里一律兜底，把 LLMError 的具体原因（凭据无效/超时/上游中断）也吞掉了，用户无法判断该重试还是该换方式。
另一个坑：`debugLog` 早期读 `process.env.DEBUG_LLM` —— Workers 里没有 `process`，线上**永远不会打日志**。已改为始终打一行简短日志（含状态码），用 `wrangler tail` / Dashboard 查看。

### 5.5 streamLLM 的 SSE 解析要点（全部是实测踩坑）
1. 上游可能把 `data: {...}` 与空行**分片乱切** —— 必须跨 chunk 缓冲到换行再解析；
2. `data: [DONE]` 是结束哨兵，收到后**仍要校验产出**（部分模型只回空 delta/推理字段，早期提前 return 会把空结果当成功）；
3. 上游 `error` 帧必须上报（`UPSTREAM_ERROR` 哨兵）—— 吃完半篇正文再来 error 帧（限流/内容审查）时，静默忽略会让截断笔记被当成功；
4. 上游不认 `stream:true` 回整段 JSON → **降级为一次性产出**保证功能可用；非 JSON 时只有 `text/plain` 才当内容（HTML 错误页不能当正文）；
5. keep-alive 注释行（`:` 开头）、`event:/id:/retry:` 行直接忽略。

### 5.6 为什么抓取用 linkedom 而不是 HTMLRewriter / cheerio
`HTMLRewriter`（Workers 原生流式解析）曾实现后回退：① 不解决抓取质量问题（质量在启发式，SPA 无 article 容器，换解析器同样抽到混合文本）；② 流式/内存优势在 2MB cap + 128MB 内存下无感；③ 双实现引入「行为一致性只能线上验证」的新成本。`linkedom` Workers 兼容、无 native 依赖、Node 单测里可直接跑。复活条件见 CONTEXT「落选候选清单」。

## 6. 数据模型

D1 单表 `jobs`（`db/migrations/0001_init.sql`），一行 = 一次流水线运行：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT (uuid) | 主键 |
| `created_at` | INTEGER | Unix 毫秒；列表排序 `ORDER BY created_at DESC, id DESC`（tiebreaker 防同毫秒顺序不稳） |
| `source_type` | TEXT | `url` / `text` |
| `source_url` | TEXT? | 仅 url 输入有值 |
| `source_excerpt` | TEXT | 正文前 100 字（列表展示） |
| `source_text` | TEXT | 原文全文（「重新生成」复用）——**列表查询不取该列** |
| `material_brief` | TEXT? | 压缩要点；未压缩为 NULL —— 列表查询不取 |
| `note_json` | TEXT? | `XhsNote` JSON |
| `status` | TEXT | `succeeded` / `failed`（未知值一律按 failed 处理，不让脏数据看起来正常） |
| `error` | TEXT? | 失败原因（用户可读） |

**读放大防护**：`list()` 用显式列 SQL（`SLIM_COLUMNS`），绝不 `SELECT *` —— 否则一次历史列表最多要把 50 × 3 万字原文搬进 Worker 再丢掉。详情接口（`GET /api/jobs?id=`）才返回全文。

**领域类型**（`lib/types.ts`）：`XhsNote { titles[3]（主+2备选）, body, tags[]（不含#） }`、`GenerationJob`、`GenerationJobSlim`（列表用，剔除全文与要点）。

## 7. 安全机制

### 7.1 SSRF 三道闸（`lib/fetch-article.ts`，用户可输入任意 URL）
1. **字面量校验**：IPv4 禁用段（0/8、10/8、127/8、169.254/16 云元数据、172.16/12、192.168/16、CGNAT、TEST-NET、组播）；IPv6 按 8 组展开判定（含 `::ffff:` mapped / compat / NAT64 / 6to4 / ULA / link-local）；拒绝 userinfo、异常端口、>2000 字符 URL。
2. **DNS 解析后校验**：Cloudflare DoH 解析域名，全部 A/AAAA 必须是公网地址（防 `<x>.nip.io` 这类解析到内网的域名）。DoH 失败默认放行（防 DoH 抖动导致功能不可用），`strictDns` 可收紧。
3. **手动逐跳重定向**：`redirect:"manual"`，每一跳重新走 ①②——`follow` 会先打到内网再事后校验，等于没防。

**残余风险（已登记）**：②与真实 fetch 之间仍有 DNS rebinding 的 TOCTOU 窗口；缓解是接口需单令牌鉴权，非令牌持有者无法触发抓取。

### 7.2 令牌与密钥
- `ACCESS_TOKEN`（可选 env）：设置后所有 `/api/*` 要求 `Authorization: Bearer <token>`；留空不校验。校验只有一处实现（`lib/auth.ts`）。
- `MAGPIE_BASE_URL` / `MAGPIE_API_KEY` / `MAGPIE_MODEL`：仅服务端 env（Void `defineEnv` 声明），前端零密钥、零硬编码。
- 前端令牌存 localStorage（自动 trim，防粘贴多空格被判 401）；`HistoryPanel` 用 `tokenReady` 闸门避免首帧 401 闪烁（token 恢复在 `useEffect`，首帧恒为空）。

### 7.3 XSS 取舍
结果区用纯文本渲染（不引入 Markdown 渲染器），无 XSS 面复制后由目标工具排版 —— 与产品①同一安全取舍。

## 8. 前端结构

