## 1. 作品集现状与能力缺口

已交付 4 个产品覆盖的能力资产：
- 同步生成（① 会议日报）、SSE 流式（② 内容工作台）
- RAG 混合检索 + 引用溯源 + 阈值拒答 + 多轮（③ 知识库问答）
- 时间序列数值 + OCR + 服务端确定性计算（④ 体检指标追踪）
- SSRF 三道闸（② 单 URL 抓取）、D1 持久化、Vectorize 向量索引

明确缺口（「下一个」优先补的）：
1. **定时 / 主动能力**：4 个产品全是「人触发 → 响应」，没有 Cron 定时、没有后台主动推送。
2. **多步 Agent（tool-use loop）**：目前都是单次 LLM 调用。
3. **多源聚合 + 变化检测**：只有② 单 URL 抓取，没有周期抓取后 diff。
4. **多租户 / RBAC**：全是单用户令牌模型。

## 3. 推荐与拍板结论

**拍板方向：A · AI 资讯雷达**（2026-11-02，用户拍板）
**产品定位：纯作品集演示**（单用户即可，弱化权限/商业化，以可演示、证据可核验为主）

**选 A 的理由：**
1. 补齐最大明确缺口——**定时 + 主动推送**（4 个产品全是被动响应）。
2. Cloudflare Workers 的 **Cron Trigger 是一等公民**；`research/zhiyu-enterprise-kb` 已验证 CF 栈能跑 Cron。
3. 复用② 抓取经验（SSRF 三道闸）+ ③ 评分/拒答经验，新技术风险可控（以 RSS 源为主，避开通达渲染老坑）。
4. 个人可用、演示性极强（每天一条日报，天然适合 show 作品集）。

**备选逻辑（未选）：** B 最稳但差异化弱；D 最有故事但最险（自主 Agent 深水区，建议作为后续进阶选题）。

## 4. 方向 A 初步设想（默认假设，待需求对齐确认）

> ⚠️ 数据源历经四轮演进（详见 `../CONTEXT.md` §3 D2）：初稿推荐 RSS → 用户要求 x.com → X 免费接口被实测证伪（session 墙 / fxtwitter 无 search，见 `方案复核-2026-11-02.md`）→ **2026-11-02 定稿回到 RSS/Atom 多源**（「自动扫描」唯一零成本可落地形态）。本文档保留当时视角，最终以 `../CONTEXT.md` §3 D1–D10 与 §4 A1–A9 为准。

- **数据源**：以 RSS 为主（HackerNews、若干 AI 博客 RSS、IT之家等中文源），避开通达渲染页面（已知边界：Workers 无浏览器内核，动态渲染页面抓不到正文）。
- **抓取链路**：Cron 定时拉 RSS → URL/标题去重（哈希）→ 入 D1 待评分队列。
- **评分**：两阶段——短 prompt 预筛热点度 + 多维评分（相关性/新颖性/实用度/权威度/情绪），取 top N 进「精选」。
- **日报生成**：每日定时把精选聚合成日报 Markdown（参考① 的板块化思路，改为资讯雷达板块）。
- **交付形态**：网页浏览「今日精选 + AI 日报 + 历史」；Webhook/邮件推送留作二期。
- **存储**：D1（sources / items / scores / daily），去重与历史回看。
- **复用资产**：② 抓取与 SSRF 三道闸、③ 评分/拒答/阈值、D1 落库。
- **风险登记**：RSS 源失效、抓取成功率（旧边界）、**Cron 配额**（CF 免费套餐 Cron 每日触发次数有限，需按免费额度设计频率）。

## 5. 待需求对齐确认的关键决策（grill 清单雏形）

1. **数据源范围**：RSS 为主 / RSS + 搜索引擎 / RSS + 社媒 API（twitterapi.io 等）

7. **语言与覆盖**：中文资讯为主 / 全球英文源为主 / 中英混合
