# ai-hot-radar AI 资讯雷达 · 交付文档

> 面向测试 / 业务方。实现细节见同目录「工作原理」文档。
> 线上地址：https://ai-hot-radar.ilikesaury.workers.dev

## 1. 功能概述

**一句话**：定时自动抓取多个 AI 资讯站点的订阅源（RSS/Atom）→ AI 按四个维度打分 → 选出值得看的 → 每天自动生成一份结构化日报。

**它替你做的事**：以前要自己刷 HN、arXiv、少数派、IT之家、几个官方博客才能拼凑出「今天 AI 圈发生了什么」。现在系统每小时自动抓一遍、打分排序，每天早上给你一份带链接和推荐理由的日报。

**四个页面**

| 页面 | 作用 | 数据来源 |
|---|---|---|
| **日报** | 每天自动生成的 6 板块日报（概览 / 头条 / 值得一看 / 分源视角 / 源健康 / 口径说明） | 定时任务每天 00:30 UTC 生成并入库 |
| **精选** | 达到分数阈值的所有条目，按分数倒序 | 数据库（只读，不触网） |
| **历史** | 已入库的全部条目，含「首次见到 / 最近见到」时间 | 数据库（只读，不触网） |
| **源健康** | 每个订阅源的状态、错误原因、抓取历史、连续失败次数 | 数据库（只读，不触网） |

**它的运行方式（无需任何人工操作）**

```
每小时 :05  抓取 6 个订阅源 → 去重 → 落库
每小时 :20  给未打分的条目打分（每次一批）
每天 00:30  用已打分条目生成当日日报（UTC，北京时间 08:30）
```

## 2. 使用说明

### 2.1 打开即用（不需要注册）

直接打开 https://ai-hot-radar.ilikesaury.workers.dev 即可。四个页签都在顶部。

> **访问令牌**：若站点配置了 `ACCESS_TOKEN`，在页面顶部输入框填入令牌后再点「刷新」。
> 未配置令牌时公开可访问（当前线上即为此状态）。**公开分享前建议配置令牌。**

### 2.2 日报页怎么看

- **一、今日概览**：今天抓了多少条、去重后多少、已评分多少、达到阈值多少、入选多少。
  末尾若显示「单源配额让位 N 条」，意思是：这些条目分数够高，但都来自同一个源，
  为避免日报被单个源占满，按规则让位给其它源的条目（不是漏抓）。
- **二、头条**：分数 ≥ 85 的条目（阈值 70 + 15 分）。
- **三、值得一看**：70–84 分的条目。
- **四、分源视角**：每个源各取最高分的一条 —— 保证不会因为只看高分而漏掉某个源。
- **五、源健康**：各源当前状态。**若某源显示「不可用」，日报里会有提示说明内容可能不完整。**
- **六、口径说明**：阈值、评分维度权重、使用的模型与提示词版本 —— 用来核对「为什么是这几条」。

日报顶部有历史日期按钮，可回看往日日报。

### 2.3 精选页怎么看

每条带**分数徽标**（0–100）、来源、发布时间和**一句推荐理由**（模型给的判断依据）。
理由是给人核对用的 —— 如果理由不成立，这条就值得怀疑。

### 2.4 源健康页怎么看

每个源显示：状态徽标（正常 / 异常（条目骤降）/ 不可用）、最近检查时间、本次条目数、历史基线、错误码。

- **展开「抓取历史」**可看最近若干次抓取的结果与耗时。
- 若出现「连续失败 N 次」标记（N > 1），说明这不是偶发抖动，**该源可能需要更换**。

### 2.5 想立刻看最新内容

点右上「刷新」：会立即抓取一次全部订阅源（不产生日报，日报仍按每日 00:30 UTC 生成）。

## 3. 权限 / 配置变更

| 项 | 说明 |
|---|---|
| `ACCESS_TOKEN` | 可选。配置后所有 `/api/*` 需带 `Authorization: Bearer <token>`；网页在顶部输入框填写 |
| `MAGPIE_BASE_URL` / `MAGPIE_API_KEY` / `MAGPIE_MODEL` | 上游大模型网关（OpenAI 兼容），用于打分。**未配置则评分功能不可用**（抓取与展示仍正常） |
| `FEED_MAX_ITEMS` | 单个源单次最多取多少条（默认 40） |
| `FEED_TIMEOUT_MS` | 单源抓取超时（默认 12000ms） |
| `SCORE_BATCH` | 每次评分任务处理多少条（默认 10） |
| `DIGEST_THRESHOLD` / `DIGEST_TOP_N` | 日报阈值（默认 70）与条数（默认 12） |
| `DB` | D1 数据库绑定（必需，存条目/分数/日报/源健康） |

密钥只存在 Worker 环境变量里，不进前端、不进仓库。

产品不依赖人工上传的数据 —— 全部来自真实订阅源。仓库内保留两份夹具用于离线 E2E：

## 5. 已知问题与注意事项

1. **RSS/Atom 源会失效**：站点改版、停更、换域名都会让源变坏。产品会如实显示「不可用」与错误分类，
   但**不会自动换源** —— 换源需要人工判断（换哪个源、主题覆不覆盖）。
2. **精选的标签集尚未人工复核**：当前 50 条评测标签由 AI 初标（阈值 70 的 Precision 100% / Recall 77.3% 即基于此）。
   标签修正后重跑 `npm run eval` 即可更新阈值，但**线上阈值需同步改环境变量**才会生效。
3. **漏选率约 22.7%**：阈值 70 优先保证「日报里没有噪音」，代价是大约每 4 条该进日报的重要资讯会漏 1 条。
   调到 65 可把漏选率降到 22.7% 以下但会混入噪音（Precision 89.5%），调低则相反。
4. **上游模型是第三方中转**：评分质量依赖该网关与所选模型；模型更换后阈值需重新标定。
5. **单源配额会让位**：某源条目过多时会被限流（当前每源最多占日报 1/3），这是刻意设计。
6. **评分是异步滚动的**：新入库的条目不会立刻出现在精选里（每小时一批，每批 10 条）。
7. **本产品只读公开订阅源**：不抓取需要登录的页面、不使用任何付费 API、不做全文爬取。

## 6. 部署与回滚要点（运维向）

### 部署

```bash
cd product5
node scripts/deploy.mjs --secrets .secrets.json
# 本机需代理时：DEPLOY_PROXY=http://127.0.0.1:7890 node scripts/deploy.mjs --secrets .secrets.json
```

脚本会依次执行：构建 → D1 迁移（`migrations apply`）→ `wrangler deploy --secrets-file` → 线上三探针。
只验证线上不重新部署：`node scripts/deploy.mjs --probe-only`。

### 部署后必查

| 检查 | 命令 / 方式 |
|---|---|
| 健康探针 | `GET /api/health` → `{"ok":true,"service":"ai-hot-radar"}` |
| 首页可渲染 | `GET /` → 200 且 HTML 含「AI 资讯雷达」 |
| D1 绑定 | `npx wrangler versions view <版本ID>` → 含 `env.DB` 与 `env.ASSETS` |
| Cron 注册 | `npx wrangler deployments status --name ai-hot-radar` 或查看 `dist/ssr/wrangler.json` 的 `triggers.crons`（应为三条） |
| 数据可读 | `GET /api/items?limit=3` → `storage:"ok"` |

> **注意**：D1 迁移只走 `wrangler d1 migrations apply`。
> 用 `d1 execute --file` 不写迁移台账，下次 apply 会重跑并报 `duplicate column`（产品③踩过）。

### 回滚

```bash
cd product5/dist/ssr
npx wrangler rollback <上一个可用版本ID>
```

回滚**不会回滚数据库**。表结构是向后兼容的追加式迁移（0001 → 0002 → 0003），
回退代码后旧表仍可读（多余列不影响）。

### 定时任务排障

Cron 触发时不会主动通知。可查：

```bash
cd product5/dist/ssr
npx wrangler tail --name ai-hot-radar      # 实时日志，能看到 [cron:fetch] / [cron:score] / [cron:digest] 的输出
```

看不到日志时，先确认 `dist/ssr/wrangler.json` 里 `triggers.crons` 是否存在，再看 Cloudflare Dashboard 的触发记录。
