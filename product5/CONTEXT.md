## 作品集定位（能力增量轴）

①②③④ 全是「人触发 → 响应」；产品⑤ 补一条全新能力轴——**聚合 + 主动扫描 + 多源**：

| 能力 | 现有产品 | ⑤ 新增 |
|---|---|---|
| 抓取 | ② 单 URL 网页 | **多源 RSS/Atom 聚合**（结构化契约，非爬页面） |
| 触发模型 | 全被动 | **手动一键触发完整流程**（抓取→去重→评分→日报一次跑完）；曾是 Cron 定时，2026-11-03 取消（D15） |
| 筛选 | ③ 检索相关性 | **两阶段评分精选，且用评测集标定**（precision/recall 可报数） |
| 持久化 | D1 | 复用（sources/items/scores/daily） |
| 向量检索 | ③ Vectorize | **不引入**（奥卡姆） |

## 1. 问题（为什么做）

- **核心问题**：4 个产品全是被动响应；AI 资讯分散在多个站点/博客/arXiv，人工逐个看成本高。需要一个「一键聚合 → 筛选 → 沉淀成日报」的主动型产品。
- **目标用户**：个人自用 / 作品集演示（纯演示定位，不做多租户）。
- **主场景**：用户点一次「刷新」，系统从多个 AI 资讯 RSS 源拉取新条目 → 去重 → LLM 两阶段评分精选 → 聚合成固定板块日报 → 网页浏览今日精选 + 日报 + 历史。**一次请求内跑完全流程**（2026-11-03：由 Cron 定时改为手动触发，见 D15）。

## 2. 范围（In / Out）

**In**
- 多源 **RSS/Atom** 订阅聚合（Worker `fetch` + XML 解析），**手动一键触发**（`POST /api/refresh`，一次跑完抓取→去重→评分→日报）。
- 默认源列表（中英混合，D4）：HackerNews、OpenAI/Anthropic/Google DeepMind/HuggingFace 官博、arXiv cs.AI、Simon Willison、IT之家、少数派 —— **每个 feed URL 在 M0 实测可用后才进源列表**。
- 两阶段评分（预筛 → 多维评分取 top N），**阈值/权重用评测集标定**（D5）。
- 跨源去重（URL hash + **L1 标题 Jaccard / L2 SimHash 指纹**，带「数字签名」硬闸，D16）、源健康监测（feed 死链 / 条目骤降报警，D10）。
- 固定板块日报生成 + 网页浏览（今日精选 / 日报 / 历史）。
- D1 落库。

**Out（明确不做）**
- **抓取 x.com / Twitter**：经三轮调研被证伪（session 墙 / 免费 API 无 search / 付费 API 被否）——见 §3 D2 演进与 `product5/docs/方案复核-2026-11-02.md`。
- **任意网页 HTML 爬取**：无契约、脆弱；RSS 之外不开放（与②「粘贴文本兜底」同理，明确边界）。
- 付费 API（官方 X / twitterapi.io / xclaw 等）、ego 浏览器、登录态 cookie（H 方案）—— 均被用户否决或无需。
- 多租户 / 权限 / 商业化；自主多步 Agent；向量检索；一期推送（Webhook/邮件，留二期）。

## 3. 决策记录（对齐结论 + 方案演进，只增不改）

- **D1 方向选定**：`A · AI 资讯雷达`，定位**纯作品集演示**；「自动扫描」定位不可变（用户明确）。
- **D2 数据源（演进，四轮）**：
  - ① 用户原要求 `x.com/home` → 三道硬墙（登录态 / Workers 无浏览器内核 / API $200 月）否决。
  - ② X 公开源 + 第三方付费 API（twitterapi.io）→ 用户坚持零成本，否决。
  - ③ X 免费接口（guest/syndication/fxtwitter）→ **实测证伪**：XActions/x-cli 文档证明 search/home 属 session 层（零登录拿不到）；fxtwitter 实测 `/2/search` 返回 404 空、无 timeline 端点（`product5/docs/方案复核-2026-11-02.md` 附录三）；xclaw.info 拆解证明其为商业服务（SSR 内嵌数据 + 30 分钟管线 + 付费 API），非零登录样板。
  - ④ **定稿（2026-11-02，用户拍板「改」）**：**多源 RSS/Atom**。X 三道墙 RSS 一条都不撞；AI 领域 RSS 源现成且高质量；「自动扫描」在 RSS 上真正可落地。
- **D3 技术选型（定稿）**：Void + React SSR + Hono 文件路由 + Cloudflare Workers + D1 + magpie LLM 网关 + **RSS/Atom 解析**（不引第三方抓取服务）；Cron Trigger 定时。**不引入** Vectorize / 付费 API / ego / 登录 cookie。
- **D4 默认源列表（中英混合，用户未另行指定）**：HackerNews、OpenAI / Anthropic / Google DeepMind / HuggingFace 官博、arXiv cs.AI、Simon Willison、IT之家、少数派。**约束：每个 feed 必须 M0 实测可用才进列表**（feed URL 不凭记忆硬编码，失效源可配置替换）。
- **D5 评分机制（强化）**：两阶段（短 prompt 预筛 → 多维评分：相关性/新颖性/实用度/权威度，情绪不评——资讯场景无意义）。**核心差异化：人工标注评测集（≥50 条「该进 / 不该进日报」）标定阈值与权重，报出 precision / recall / 漏选率**——方法论平移自产品③ 的四指标标定，①②③④ 均未做过「筛选标定」。
- **D6 呈现形态**：固定板块日报（参考① 6 板块）+ 今日精选列表 + 历史回看。
- **D7 一期交付**：纯网页，推送留二期。
- **D8 存储与频率**：D1 落库（sources/items/scores/daily）；Cron 频率默认 **每 1–2 小时抓取 + 每日 1 次生成日报**（受 Free 套餐与 feed 礼貌间隔约束，可配）。
- **D9 零成本约束**：不引入付费服务、不引入独立运行时；Workers Free 的 **CPU 10ms / subrequest 50** 为硬预算（A9 护栏）。
- **D11 精选多样性配额（新增，2026-11-02 线上实测触发）**：实测 top5 全为 `arxiv-cs-ai`（该源日更 40 篇、权威度天然高），
  单一源会垄断精选。固定规则：**同一源最多占精选的 1/3**（`topN=12 → 每源上限 4`），
  溢出名额顺延给次高分条目；日报同理。实现落 `lib/digest.ts` + `selectTop` 的 quota 参数（增量 4）。
- **D10 源健康与降级（新增）**：feed 失效是常态而非异常——按「HTTP 非 200 / 解析失败 / 条目数骤降」三级登记源状态并在 UI 可见；单源失败不影响其它源（降级不放大）；错误文案面向用户（沿用③ 401 与失败分开的教训）。
- **D12 源健康口径修正（新增，2026-11-03）**：「**被 maxItems 截断**」不等于「**源异常**」。
  旧实现把两者混为一谈 → 真实 895 条的 hf-blog（只取 40）与 60 条的 ithome 天天报 degraded，UI 上像坏源。
  修正后：只有**真条目骤降**（相对基线 <40%）才 degraded，截断由 `truncated` 字段透传而不污染健康等级。
- **D13 源列表扩充与「官方源优先」（新增，2026-11-03，用户拍板）**：源从 6 个扩到 **14 个**，
  定位改为**官方一手来源优先**（openai / deepmind / google-ai / aws-ml / nvidia / arxiv + 社区与媒体），
  权威度契合四维评分。硬约束（Cloudflare 官方 limits）：Cron **CPU 10ms**、外部 **subrequest 50/次**、
  内部 D1 **1,000/次**、账号 **5 个 Cron**。因此：`maxItems` 由 40 降到 **15**（实测解析耗时随条目数线性增长、
  与文档大小几乎无关），D1 写入改走 `db.batch()`（整批计 1 个 query）。
- **D14 arXiv 端点失效与替代（新增，2026-11-03）**：`rss.arxiv.org/rss/cs.AI` 上游已失效
  （返回 892B 空壳、0 个 `<item>`，cs.CL / cs.LG 同样）→ 改用官方 Atom API
  `export.arxiv.org/api/query?search_query=cat:cs.AI&...`（实测 40 条 / 日期齐 / 摘要 40/40）。
  同批移除 **hf-blog**：该 feed 不提供任何摘要（实测 0/40），预筛必然全丢、占库存零贡献。
- **D15 取消全部定时任务，改为手动一键触发完整流程（新增，2026-11-03，用户拍板）**：
  原架构有 3 个 Cron（抓取 `:05` / 评分 `:20` / 日报 `00:30`），本轮**全部删除**，改为
  `POST /api/refresh` 一次跑完「抓取 → 去重 → 评分 → 生成日报」，前端「刷新」按钮直接调它。
  **理由**（三条，均是实测/推理得出，不是偏好）：
  1. **定时抓取只堆不消**：实测每轮抓 195 条，评分 cron 每小时只消化一批 → 队列长期积压（实测 pending 558）。
  2. **评分是花钱的**：定时跑意味着每天固定烧掉一批 LLM 额度，而用户可能根本没看。
  3. **用户要的是「点一下就看到新内容」**，不是「等 cron 慢慢磨」。
  **代价与取舍**：抓取频率由「每小时」变成「用户手动决定」—— 对个人自用/演示定位是合算的；
  **批量化评分（方案 D）因此变得更有必要**，因为现在一次点击必须把队列消化得足够快。
  **附带修正**：页面**初始加载不再调 `GET /api/feed`** —— 那个接口本身就会抓源站，
  等于「每次打开页面都自动抓 14 个源」，与本决策相悖；`GET /api/feed` 保留为「源站可达性探针」
  （部署脚本与 E2E 依赖它）。
  **运维坑（已踩）**：`wrangler deploy` 与 `wrangler triggers deploy` **只增不删** cron，
  删掉 `crons/` 目录后线上仍残留 3 个旧触发器 → 必须用 Cloudflare 的
  `PUT /workers/scripts/{name}/schedules`（**替换语义**）清零。已写进 `scripts/deploy.mjs`。
- **D16 L1/L2 标题去重，带「数字签名」硬闸（新增，2026-11-03，用户拍板）**：
  目标是**省 LLM 调用** —— 同一事件被多源报道时，逐条评分是纯浪费。
  **两层判据**（`lib/dedup.ts`，纯 CPU、零 API、零配额）：
  - **L1**：归一化标题 → token 集合（英文按词 + 中文按字符 bigram）→ **Jaccard ≥ 0.55**
  - **L2**：**SimHash 64 位指纹** + 汉明距离（跨批次主力，可持久化）
  - **硬闸**：**数字签名**（标题里的版本号等数字）不同 → **绝不合并**。
  **阈值是标定出来的，不是拍的**（`scripts/calibrate-dedup.ts`，14 源真实数据 240–280 条）：
  - 纯 Jaccard 会**把不同版本的公告合并**（「Introducing Gemini 3.8 Flash」vs「…3.6 Flash, 3.5 Flash-Lite」
    实测 jaccard **0.800**、汉明 6）—— 合并 = 丢资讯，不是省调用。加数字签名闸后假阳性全消。
  - 阈值扫描：≥0.50 → 合并 4 对（含 1 对假阳性）；**≥0.55 → 合并 2 对（均为真重复）**；≥0.667 → 漏 1 对。故取 0.55。
  - **SimHash 单独用不安全**：汉明 12 的「Quoting Ted Sanders / Quoting Jason Koebler」是完全不同的文章。
  **集成位置**：`lib/queue.ts` 的**预筛之后、送 LLM 之前** —— 命中重复的条目标 `dropped`（记原因），一次调用都不花。
  **跨批次**：与最近 3 天**已评分**条目比（同事件跨轮次报道：openai 上午发、hn 下午转）。
  **未做**：embedding + Vectorize 聚类（原理成立但 Workers Free 下 CPU 超 39 倍、神经元超 50%、查询维度超 4.8 倍，
  详见 `product5/docs/` 与本轮调研记录）；等评测集证明 L1/L2 召回不够时再上，产品③ 的封装可直接搬。
- **D17 批量粗筛 + 逐条精排（新增，2026-11-03，用户拍板「D」）**：
  **问题**：逐条评分「调用几百次不可想象」。调研的同类项目（`news-that-matters` 等）都是
  「先廉价筛选、后少量 LLM 精排」——200 条只花 **6 次**调用，我们逐条评是 200 次。
  **三层设计**（`lib/coarse.ts` + `lib/queue.ts`）：
  1. **L1/L2 去重**（D16）先跑 —— 重复条目连粗筛都不做。
  2. **批量粗筛**：一次调用打包 10 条 → 粗分 0–10。**批量 10 的依据**：
     RoBatch（arXiv:2605.28268）实测新闻分类批量 ≤16 准确率保持、>16 就掉，
     且成本曲线在 8–16 区间已压平（无缓存下每百万条：1→8 降 75%，16→64 只再降 21%）。
     取 10 = 离悬崖留 60% 余量。
  3. **逐条精排**：按粗分排序取 top 20，用**现有 score-v1 prompt** 逐条评 →
     **阈值 70 的语义完全不变，评测集不用重做**。
  **三条硬规则**：
  - **粗分只用于排序，绝不用于阈值判断** —— 阈值 70 是用逐条精排 prompt 在评测集上标定的
    （Precision 100% / Recall 77.3%），批量分数分布与逐条不同，套 70 会失真。
  - **粗分必须落库**（`items.coarse_score`，迁移 0007）—— 粗筛一次、多次用。
    用户点第二次「刷新」时，队列里已有粗分的条目**跳过粗筛**，预算全给精排。
    实测这让「多次点击」能累积精排量，最终填满精选配额。
  - **粗分必须按 id 校验** —— 漏掉的 id **单独重试**（不是整批丢弃）。
  **实测收益**（本地 E2E 断言调用次数）：堆积 29 条 → 粗筛 3 次 + 精排 20 次 = **23 次**
  （而非 29 次）；线上稳态（新增 4 条）→ **跳过粗筛**（coarseCalls=0），因为
  4 ≤ 精排上限 20 时粗筛反而多花一次调用。**这是刻意设计**：稳态不粗筛、堆积才粗筛。
  **踩到的坑**：认领了但没精排的条目会被**租约锁 10 分钟**，用户点第二次刷新时认领不到它们
  —— 而它们的粗分已算好、只差精排，白白浪费。修法：新增 `store.releaseClaims()`，
  本轮结束前把「认领了但没处理」的条目释放掉。

## 4. 验收标准（写死）

| # | 验收标准 | 判定方式 |
|---|---|---|
| A1 | Worker 在真环境拉取 **≥3 个 RSS/Atom 源**并解析出条目（标题/链接/时间/摘要），feed URL 全部来自可配置源列表 | 真环境探针（M0）+ 集成测试 |
| A2 | 跨源去重：同 URL / 同内容 hash 不重复入库 | 单测 + 重复拉取验证 |
| A3 | 两阶段评分产出多维分 + 综合分，top N 进精选；**阈值/权重由评测集标定，报告 precision / recall / 漏选率** | 评测集脚本 + 单测（评分纯函数） |
| A4 | **一次手动触发完成「抓取 → 去重 → 评分 → 生成日报」**，日报为固定板块 Markdown 写入 D1 | `POST /api/refresh` 返回汇总 + 查 daily 行 + 单测聚合（D15 改口径：原为 Cron 分批） |
| A5 | 网页可浏览：今日精选 + 日报板块 + 历史 | 浏览器/接口 E2E |
| A6 | 单源失败（死链/解析失败/超时）**不影响其它源**，源状态三级可见，文案面向用户 | 注入故障的单测 + 真环境坏源用例 |
| A7 | magpie key 仅存 Worker env，不进前端/仓库 | 构建产物 grep + 代码审查 |
| A8 | **手动一键触发完整流程**（原验收口径为「Cron 按配置频率触发」）| 线上 `POST /api/refresh` 实测 + 线上 cron 触发器已清零（D15） |
| A9 | 单次触发在 Workers Free 下不超 **外部 subrequest 50**（实测计数；超了降批量或承认需 Paid） | 真环境实测 subrequest 计数（抓取 14 + 评分 ≤30 ≤ 50）；CPU 读数仍标估算 |

## 5. 关键决策（索引）

- 数据源走 RSS/Atom 结构化契约（D2-④/D4）——「自动扫描」唯一零成本可落地的形态；任意 HTML 爬取明确排除。
- 评测集标定精选（D5）——把「筛选」从玄学变成可报数的指标，作品集核心差异化。
- 源健康三级状态 + 降级不放大（D10）——feed 失效当常态设计，沿用③ 错误分类教训。
- Free 套餐硬预算（D9/A9）——小批量设计，实测计数兜底。
- **取消全部定时任务、改为手动一键触发完整流程**（D15，2026-11-03）——定时抓取只堆不消，且**评分花钱**而用户可能根本没看。
- **L1 标题 Jaccard + L2 SimHash 指纹去重，带「数字签名」硬闸**（D16）——同事件多源报道只评一次，省 LLM 调用；版本号不同绝不合并。
- **批量粗筛 + 逐条精排（方案 D，D17）**——粗筛 10 条/次打包一次调用，只用于**排序**；精排仍是逐条 score-v1（阈值 70 语义不变、评测集不重做）。粗分落库 → 一次算多次用。
